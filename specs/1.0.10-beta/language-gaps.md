# Language gaps — 1.0.10-beta

The compiler is frozen for every **library** front. Every library front is built from plain botopink
plus `@Decl`, comptime, `@emit` and `#[@External.<Target>]`, and a library front that needs a
compiler change does not get one. What it does instead is write the nearest form that parses today,
mark the line `// LANGUAGE GAP:`, and record the gap here.

The compiler is **not** frozen for [`00-compiler-carry-over`](./00-compiler-carry-over/README.md),
which carries the open compiler fronts. The last column of every table below says which of those
fronts a gap belongs to, or `—` when it belongs to none and stays a library-side workaround. A gap
owned by `00` is **still worked around** by the library front that hits it — `00` runs beside the
libraries, not ahead of them.

The exit gate in [`fronts.md`](./fronts.md) requires every `// LANGUAGE GAP:` marker left in an
example to appear in a spec here — a gap that exists only as a comment in a `.bp` file is a gap
nobody will fix. Rows are added as fronts are written and removed when the gap closes. A row names
the gap, where it bites, what the nearest valid form is today, and what surface would close it.
