## module-system — files, modules, imports and the build layer

**A file is a module, the build has a layer of its own, and an import names where its names come from.**

(1) Every `.bp` under `src/` is a module of the package, its path its name (`pages.home`, `comptime.route`); no `lib.bp`, no `mod` / `pub mod` (592 (1)). `src/main.bp` is an executable's entry (`pub fn main()`), imported by no module; a library has none (592 (2)); the manifest's `"entry"` is an executable's alone — `main.bp` when absent — and says only where execution starts, never narrowing what the package holds (677); a library has no entry, and the key in a manifest with no `main` is refused, `manifest-entry-in-library`, located at the key (733, 592 (2)). `src/comptime/` is the build layer: analysed before every other module, it imports only std, dependencies and `src/comptime/` itself, and a decorator or a template is declared only there, in std or in a dependency — else refused, located (592 (3)). `src/internal/` is private to its package; every other `pub` item is the package's API (592 (8)). The prelude of a package is any marked `pub` item outside `internal/` (592 (9), 589). `botopink.json`'s `files` is gone: what a consumer may import is the tree; once B-69 / B-75 land a manifest still writing `files` is refused, located, naming `src/internal/` (703).

(2) **Every module is in the program.** Every module under the root's `src/` is checked, compiled and linked, imported or not, and its `compiler.init` executors run in 580's order (677); every module of every declared dependency joins the build the same way — `import` brings names into scope and nothing else; being declared is what makes a package's registrations run (660). The init list is ordered by dependency resolution: a package after every package it depends on, by the deepest chain, two packages of one level in the depth-first order the manifests give; inside a package, 580's order (660, 676 (1), (2)).

(3) **Blocks and order.** Modules importing each other form a block (a strongly connected component); a block's headers (`fn` signatures, types, annotated `val`s) are registered before its bodies; at run time a module-level `val` is a ref, a memoised getter (commonJS hoists its functions onto `exports` before any `require`) (592 (4)); a module's body — its `val`s, `var`s and `_` statements — runs once, in declaration order, when the module loads and before `main`, an imported module's before its importer's, dependencies first, and a `pub val` of any type is imported and read like a `pub fn` (140, 580, 660). Per block: headers, bodies, then every decorator over them, then every meta of the block is filled (592 (5), 728). The only order refusal is `dependency loop`, located: a value needing itself across modules, or a `comptime` needing a meta or a value of its own block before its decorators ran (592 (6)). Until B-72 analyses every body of a block before its decorators, a `comptime` reaching a function declared after it whose body holds a template call is refused at the `comptime`, naming the call and the remedy (702).

(4) **Imports.** `import {…} from "<name>"` resolves only to a package — std, a bundled package or a declared dependency; a module of the importing package is imported by its path in braces, with no `from` (`import {log.logger};`, `import {a.b.c as d};`); `from "<a module of this package>"` and `from "<the package's own name>"` are `error[module-import-with-from]` at the source string, the brace form the fix, std included (`import {path.relative};`) (206, 309). The brace form reaches the package's internal declarations as well as the exported ones; a package's tests are its modules too (309). A bundled package added later never changes what an import means (206). Only a direct dependency is importable: `import {rkProp} from "rakun";` with only `rakun-starter-web` declared is `error: unresolved import source "rakun" — declare it in botopink.json "dependencies"` (242). The shorthand import is gone: an item whose first segment names no module of the package and that has no `from` is `error[shorthand-import]`, its fix written (337 (1)); 337 (2)'s `mod m;` namespace binding is replaced by 592 (1) (no `mod`). No combined form, no re-export syntax (337 (3)).

(5) **Namespaces and defaults.** `import {a.b}` and `import {a.b as X}` bind the namespace of the module `a/b`; written as a value — called, passed, bound — the namespace is the module's `pub default`, and `Card.Props`, `Card.render` reach its items; a namespace of a module with no default written as a value is refused `namespace-not-a-value`, located (582 (1)). `import {a.b.p}` binds the item, `import {a.b: {p, q}}` the items (582 (2)). A dotted path and a braced group are one tree — the dot for one leaf, the braces for several under one prefix — and only the leaf enters scope: `import {io.fs.readText}` brings `readText`, neither `io` nor `fs`; an intermediate node is a leaf when listed (`io: {fs, fs: {readText}}` brings both) (107); an imported folder module is a namespace of its submodules, so `import {io}` makes `io.fs.readText(p)` resolve (110 (2)). An imported `implement` / `extend` enters scope only when activated with `*` on its item (`collections: {ArraySets*}`), each extension opt-in by name; `*` on a namespace is refused, and `as` on a `*` leaf is `import-alias-on-activation` (107, 110 (3)). `import {pkg} from "pkg"` and `import pkg;` are one form: the package's namespace, its default the default of `src/<pkg>.bp` (582 (3)). `a.b` names either an item of `a.bp` or the module `a/b.bp`; a package holding both is refused `module-item-collision`, located at both (582 (4)). A module declares a default beside other `pub` items (582 (5)). A module's default function may be anonymous — `pub default fn (…) -> R { … }` binds no name; `pub default <name>;` makes an existing function the default; `pub default fn Name(…)` is the shorthand of both; the importer names the default (the module path's last segment, or an alias); an anonymous default's name is the module's file name (289, 213).

(6) **Aliases and same names.** An import that names its source says which declaration it means and is never `ambiguous-import-use`; two aliased imports of one name from two sources are legal, types too (`import {m1.T as A}; import {m2.T as B};`), each alias naming its own type in every position, every backend qualifying a type by its module; an un-aliased pair stays refused, `import-name-collision` (170, 310). A type of this module beside an aliased import of a same-named type is two types — identity is module + name (603); so two same-named types of two packages are two contexts too (635 points at 603). A name written between backticks is an identifier anywhere a name goes (Kotlin's escaped identifier): `` `not-found` `` — any characters but a backtick and a line break, a keyword included —, so a `.bpp` whose name is no identifier is imported `` import {pages.`not-found` as NotFound}; `` or without an alias; `` `count` `` means `count`; each backend maps the name deterministically and the diagnostic prints the backtick form; an empty `` `` `` is refused at the lexer (561).

(7) **`import-of-failed-module`:** one error per importer at its import item — "`<name>` comes from `<module>`, which failed to check — its own errors are reported there (`<path>`)", one text for a name and a namespace; the refused module keeps its own error (545). Two files of one module path stay refused by the twin rule (`x.bp` beside `x.bpp` or `x/mod.bp`); no `.d.bp` exists (693, 575 (1)).

Not the rule any more: `lib.bp`, `mod` / `pub mod`, the catalogue in the root and 592 (7)'s catalogue (no catalogue is read at build; what stands of s23-i is 592 (2)'s `src/main.bp`, 729, 665), the "prefix module wins" rule and `expandImports` (592, 582); `from "std"` inside std (309); onze's (now `rakun-ssr`'s) `@/` alias (218, under § rakun-ssr).

## manifest-and-dependencies — `botopink.json`, targets, dependencies and workspaces

**The manifest is the single source of truth for what a package runs on and depends on; a restriction is checked, never listed.**

(1) **Targets.** `test-libs` and every runner run a member on the targets its manifest declares and no other; `scripts/restricted-targets.txt`, `scripts/known-red-libs.txt` and `--include-unsupported` are gone (153). A `"targets"` narrowing is honoured everywhere and audited: a cell or member may exclude a target only when `botopink build --target <t>` refuses it with a host-binding error (156); `#[beamMemory(…)]` off the BEAM is accepted with no effect (547), so that exemption is gone (167 as amended by 547). Every declared dependency's `"targets"` holds every target of the package that declares it, checked at the dependant's manifest at the dependency's line, `dependency-target-missing`, naming the package and each missing target, whatever target the build is for, transitively (676 (3)); a package with no `"targets"` holds the intersection of its dependencies' (and its workspace's, when a member), and only a declared target a dependency lacks is refused (770). A `test/` suite that narrows its targets is a project suite — a directory with a `botopink.json` naming `"targets"`; a single file declares no narrowing and the `// targets:` line is gone (536). A wasm build names its host, `"wasm": { "host": "wasi" }`, absent meaning `wasi` (334 (2)). The `.d.ts` emission is switched by `"typings": true` in the manifest or `botopink build --typescript`; each only turns it on, there is no `--no-typescript` and no `"typings": false` (619, 620).

(2) **OTP.** The compiler emits for one exact OTP release (28 — one constant, printed by `botopink --version`); `build` / `run` / `test` on erlang or beam refuse another `erl` on `PATH`; a manifest's `"otp"` must be a release the compiler supports, every package of a closure that declares one agreeing; `gate.sh` and the workflows take the release from the compiler (228).

(3) **Dependencies.** `dependencies` is the object form alone — `{ "<name>": { "path": … } }`, `{ "git": …, with exactly one of "branch" | "tag" | "rev" }` or `{ "workspace": true }` —, a string array a located error (76, 75). A `git` dependency may name a package inside its repository, `"subdir"`: cloned once at `ref`, its `path` dependencies resolved inside the same checkout; refused, located: `subdir` without `git`, absolute or leaving the checkout, with no `botopink.json` or a workspace manifest, one repository at two `ref`s (344). A project's dependencies are found in its own `.botopinkbuild/deps/<name>/` first, as `node_modules`; the walk-up to an enclosing `repository/` is a fallback (`BOTOPINK_LIB_ROOTS` first when set); `bpmp link` links each dependency to a local checkout; CI keeps `bpmp install` (483 (1), (2)). A library's gate finds the compiler at `<project>/.botopinkbuild/bin/botopink` first (483 (3)). `scripts/worktree-add.sh --repo <lib>` makes the library's worktree alone and links the compiler (483 (4)). The package name `std` is the bundled standard library's alone: another `botopink.json` named `std` is refused at the manifest (453). The walk-up stops at the first ancestor that holds `repository/` — the enclosing checkout: the meta workspace, a worktree of it, CI's — and never reaches another checkout's libraries, one predicate (`manifest.isCheckoutRoot`) serving the compiler's loader, `botopink-lib-test` and the language server; dependencies are transitive — each dependency's own entries resolve from its manifest and directory, every package loaded once by import name after every package it depends on —, and one import name two packages resolve to two directories, or a cycle between packages, is refused at the entry that brought it in (143).

(4) **Workspaces.** A library's umbrella `botopink.json` is a workspace, never a package — `"workspaces": ["modules/*", "examples/*"]`, no `src` / `entry`, importing it a located error; `{ "workspace": true }` is the only way a member depends on a sibling, a `path` to one refused; `test-libs` and `botopink test` run every member, examples included, and report per member (75). A workspace declares what its members share; a member declares only its own: a member's `name` is required and unique (refused, located, when missing or repeated), so no two members emit a module of one name; the workspace's `dependencies` are inherited, a member may add its own, redeclaring an inherited one is refused; `targets` and `otp` inherited, a member only restricting `targets`; `src`, `entry`, `version` default to the workspace's (512). Every `conformance/modules/` is such a workspace (`"workspaces": ["*"]`), so a library's cells share one dependency closure and one cache (512 (5), 509 (4)). A cell's package name is its directory's (511). `workspaces` stays when `files` goes (703).

(5) **Configuration in JSON, case by case:** `botopink.json` stays as clean as possible; a configuration may live in it or in another JSON file, decided case by case; `"bpp"` is required, one package name, `"bpp": "rakun-bpp"` (284, 361 (4)).

## caches-and-build-outputs — where a build writes and what it may reuse

**Every cache lives under `.botopinkbuild/`, only dependencies are cached, and nothing a test exercises comes from a cache.**

(1) Every build cache lives under `<root>/.botopinkbuild/cache/` (`<root>` the workspace root, else the project root): deleting `.botopinkbuild/` deletes it all; `botopink clean` deletes it whole; `gate.sh --cold` deletes the cache of every root it reads; nothing in `$HOME` or `$XDG_CACHE_HOME` (225). The language server's cache is `.botopinkbuild/cache/lsp/` of the opened project; `~/.cache/botopink-lsp` goes (233).

(2) **One code cache, the CLI's, for every target.** The package under test — a cell's own package, the member whose tests run, the project built or run — is always analysed, generated, compiled and run; only its dependencies may come from the cache (509 (1)). Level A, first: every target's toolchain step after the codegen, for a dependency's modules, under the key of its input bytes and the tool's version (erlang `.erl` → `.beam` with the options and the OTP / erts / `compiler` / `stdlib` versions, a source with `-include` or `parse_transform` never looked up; wasm's assembly and its runtime's precompile) — one mechanism, replacing `cache/erlcheck` and `cache/beam`, read by `build`, `run`, `test` and `cell check` (509 (2)). Level B, later and only after the invariant "a package's analysis and generated code depend on its dependency closure alone" is proved by a test: a dependency's checked interface and generated code per target (509 (2)). The closure key is a hash of the package's files by content, its dependencies' closure keys (Merkle), the target and the compiler's sources by backend partition, never the binary's hash alone (509 (3)); the partition is `codegen/backend-partition.txt` — every source not assigned to one backend is shared and in every key (249). An entry is stored by hash, never by name; a program never runs from the cache — an entry is materialised (hard link, else copy) into the project's output (509 (4)). a cold run — `scripts/gate.sh --cold`, botopink itself having no `--cold` (739, 754) — reads nothing and writes what it ran; CI and a landing run cold; only a success is stored, nothing when a key cannot be computed with certainty; concurrent writers stage and rename, no lock (509 (5)). B-77 then makes `botopink cache` the one place of the build infrastructure: level A moves to `.botopinkbuild/build/` beside level B's `.botopinkbuild/analysis/`; `cell check` and `test` take their jobs from the machine's pool (468 / 473's directory and formula, moved into botopink) and report in the units' order; `--jobs` and `--cold` leave `build`, `run`, `test` and `cell check`; `botopink cache clean` / `status` are its own section of `--help`; the scripts and the libraries' runner keep only the hook's flags (`--staged`, `--no-conformance`), losing their cache logic and the pool; botopink knows cells and workspaces only, never a conformance suite, a hook or a CI (739). Every file `compiler.embed` reads joins the closure key (519, 607 (1)).

(3) **No test result is cached:** a pass is never stored nor answered from a store; the result store of `cache/results/lib-test` is removed; a gate is made fast by the code cache and by running only what a change reaches, never by skipping a run (510).

(4) **Units.** A module's tests are a unit of their own; its production unit is the same in `build`, `run` and `test`: every module emits its production unit always and, under `botopink test` of the package under test only, a test unit holding its `test` blocks, marked by the `__test__` prefix (erlang `'__test__@rakun-stylesheet@spacing'`, commonJS `__test__/rakun-stylesheet/spacing.js`, wasm linked only under `test`); a type's unit keeps `@@` (513 (1)). A test reaches a private function or module `val` through a reserved export the production unit always carries (`'__bp_priv__<name>'/N`, one hidden export object on commonJS, none on wasm); the runner is one, at the test entry (513 (2)). A dependency's test units are never emitted for a consumer; a test unit is never cached (513 (3)). A dependency's module set is one in every command: with no `.d.bp`, a dependency's module that does not check is refused by `build`, `run`, `test`, `check` and `cell check` alike (514, 515, 586, 575 (1)). In a project whose modules sit in folders, a module in the project's own `src` belongs to the project, never to a dependency named after its first folder; a type's compiled units are written beside the module that declares it (317).

(5) A trace's listing is lowered again from the module's Erlang text each time a snapshot or the code cache reads it; the wat build cache keeps the Erlang text, never the listing (692).

(6) **Output layout and atoms.** The erlang and beam outputs are flat, one directory per target (`out/erl/`, `out/beam/`), each file named by its module atom; commonJS and wasm keep `out/<module path>` (6, 109). A module's BEAM atom is `<package>@<path>` — the `botopink.json` `name`, then the module path with `/` as `@`, lowercase, any other character `_` — and a declaration's is `<module>@@<Decl>` with its case kept (`std@math`, `std@io@fs@@File`, `myapp@main@@SourceLocation`), one rule for a `type` and for the `val` an `implement` is bound to; the same atom is the value's identity on both BEAM targets (109, 21); a package name must start with a lowercase letter, refused at the manifest and by `botopink new`; a compilation with no `botopink.json` is refused on erlang and beam, nothing guessed from a directory; the compiler's tests compile as the package `test`, the comptime's modules as `bp`, a package named `bp` refused; two declarations of one module whose atoms differ only by case are refused (109). A `behavior` emits no module (23, 109).

## prelude-and-primitives — what every program sees without an import

**The prelude is `primitives.bp` alone; a primitive is a lowercase type, a capitalised name is a contract several types share; `print` and `panic` are imported.**

(1) **One prelude.** The types and behaviors a program reaches without an import — `Result`, `Task` (now `Async`, 553), `Component`, `Renderable`, `Iterator` (now `Iter`), `Stream` (now `AsyncIter`), `Future`, `Use` — are declared in `primitives.bp`, registered before every module, and written bare everywhere; a local declaration shadows a prelude name, as it does `string` and `array` (606 (1), 641), a literal's type excepted (639, below). `TypeInfo` is no prelude name: it is `compiler.Info<T>`, declared in `compiler.bp` and imported by path (606 (3), 608, 630). No `#[builtin]`, no `@name`, no `compiler.setBuiltin`, no `builtin-twice` (606 (1); replaces 575 (2)). No `.d.bp` exists: the declaration-file kind is gone, every `.d.bp` renamed or dissolved into the std module that owns each declaration; a file still ending `.d.bp` is a module named `x.d` (575 (1)). Every builtin that remains is a declaration in std (252 as carried by 575 (1), 606).

(2) **Two std functions, imported where used,** inside std by the same import: `print(..values: unknown[])` in `io/terminal.bp` (`import {io.terminal} from "std"; terminal.print(…)`) and `panic(message: string = "panic") -> noreturn` in `failure.bp`, beside `Failure` and `attempt` (606 (2)). `println`, `debug` and `todo` are removed (`println(a, b)` is `print(a, b, "\n")`, `todo()` is `panic("not implemented")`); `src` is `compiler.src()` (606 (2), 718). `print` is an effect and never folds at build (632, 682).

(3) **Primitive types are lowercase and are types:** `i32`, `i64`, `u32`, `u64`, `f32`, `f64`, `bool`, `string`, `bigint`, `bytes`, `array<T>` (`T[]` stays the spelling of `array<T>`), declared `pub type … implement <contract>` in `primitives.bp`; neither `Pair<A, B>` nor `Function` exists — a pair is the tuple `#(A, B)` (`#(a, b)`, `p._0`, `val #(a, _) = p`), and `identity`, `compose`, `flip`, `constant` are plain functions of std's `functions.bp` (738); a capitalised name is a contract shared by several types (`Number`, `Integer`, `Signed`, `Float`); `String`, `Bool`, `BigInt`, `Bytes` and `Array` dissolve into their types, which hold their methods and statics (641, 617 (1)). A behavior holds signatures and `default fn` bodies in botopink, never a cell — the body is the algorithm for every type that does not override it (617 (2)); host code lives on the type, `#[compiler.external(…)] declare fn toString(self: Self) -> string;` inside `pub type i32 implement Signed { … }`, `Self` concrete (617 (3)); a type overrides a `default fn` by declaring the member itself (617 (3)); `implement-with-body` holds on every bodied declaration, a behavior's `default fn` included (617 (4)). A static with a cell is the type's static — `string.fromCodepoint(65)`, `array.range(0, 3)`, `bytes.fromUtf8(s)`, `bigint.of(…)` — declared on the type, never on a behavior; a contract may list a required static (`fn make() -> Self;`) each type provides (641). In a `behavior`, a member without `self` is a static of the behavior and is written `fn`, never `default fn`: `fn unit() -> Self { … }` with a body is the behavior's own function, `fn make() -> Self;` without one a static each implementor provides; `default fn` is an instance member with an overridable default body; `default` on a member without `self` is refused, `default-on-static` (628). A module declaring a type named like a literal's type (`i32` … `bigint`) is refused at the name, `primitive-type-redeclared` — the structural exception to shadowing, exactly the types the language gives to literals (639). A type that implements a behavior only through an extension block (`Sym implement B for T`) is not a value of that behavior (684). There is no `any` — no type turns the checker off; `unknown` is the host vocabulary's spelling, narrowed with `is` before use (31). A primitive receiver answers only the methods its type declares — a `fn`, a `val`, `len` / `size` for `length`, an `extend` block's —, anything else `unknown-primitive-method` at the name, suggesting the declared method whose host spelling or near name was written; a host spelling (`toUpperCase`) is no method of the language (136). An index is sugar for a method call and has no typing rule of its own: `xs[k]` is `xs.at(k)` and answers `?T`, `d["k"]` is `d.at("k")`, `xs[a..b]` is `xs.slice(a, b)` and `xs[a..]` `xs.slice(a, null)`; `at` and `slice` come from the ambient behaviors `Index<K, V>` and `Slice<V>` of `primitives.bp`, which `array<T>`, `string` and `Dict<K, V>` implement and any type may (63, 46, 30); a tuple's constant index is the checker's own case (63, 139); an absent index or key answers `null`, the one spelling of absence (47); a negative position counts from the end on `array` and `string` alike — `xs.at(-1)`, `xs[-1]`, `"abc".at(-1)` —, `Dict.at` by key (139).

## host-functions — `declare fn`, `#[compiler.external(…)]` and `Implementation`

**A bodyless `declare fn` names its host sources with `#[compiler.external(…)]`; a source is host code a target runs, written by its label; a call with no cell for the active target is refused.**

(2) **Labels.** Only the `template` is positional; every other field is written by its label, in any order; a second unlabelled argument is refused, `external-field-unlabelled`, naming the label (621, 487, 305). ## syntax-and-comptime-parameters — how an argument arrives

**`comptime x: T` receives a value known at build; `syntax x: T` receives the code as written, not executed at the call; a `-> anytype` / `anyvalue` function builds a type or code; there is no `Expr<T>`, no `.value`, no `Decl`.**

(1) **The two modifiers.** `comptime x: T` is a value known at build, the body holding a `T` (575 (4)); an ordinary function's `comptime` parameter is its specialisation, and an argument not known at build is `comptime-arg-not-known`, read or not (417, 670). `syntax x: T` is the expression written, captured as a tree, opaque in the body — handed only to `compiler.*` or into another tree; a decorator's first `syntax` is the annotated declaration (575 (4), 576 (10)); the modifier is named `syntax` (`expr` is gone), exact for a declaration, an expression or a lambda (616). A `syntax` parameter accepts any expression — a `comptime` value, another `syntax` value, a run-time expression — checked once by the ordinary type check; it guarantees the argument is not executed at the call: the compiler holds the code and evaluates it only where it splices it, so the expression's stage counts there and never at the capturing call (720, 716). `@Expr<T>`, `.value`, `x.fail(…)`, `Decl<T>`, `@Decl`, `Declared<T>` and the old modifier are gone (575 (4), 576 (1), (7)); a `comptime` variadic is one array, `comptime ..sources: Implementation[]` (575 (6), 412 as carried); an optional function-typed `comptime` argument is tested against `null` as any `?T` is — `if (rule == null) { … }` — the function type no exception, 411's `expr-value-of-function` gone with `.value` (735, 575 (4)); the parameters' spelling is 731 (11). `comptime t: type<T>` takes a type and binds `T` (`compiler.typeInfo(city)` with a value is refused); `type<T>` is the type of the type `T`, `anytype` the bare `type` renamed — a type not known until it is built —, `type(` / `type {` the inline type (575 (5), 578 (2)). A function's type parameter is always bound by a parameter, never by the return type alone: `fn get<T>(self: Registry) -> ?T` is refused, `type-parameter-unbound`; `comptime t: type<T>` binds it as Java's class token (668, 667). `v is T` with `T` a type parameter is refused at the test, located, `is-type-parameter`, naming the parameter and the form that works: `v is t` with `comptime t: type<T>`, the concrete type's test in the function specialised for it — a copy per type argument, `t` the type inside it, so `t` handed on to another call is a `comptime` argument known at build (667, 757); or as `t: type<T>` without `comptime`, a run-time value — the type's identity (603), crossing as `Field(Book, "pages")` does (631) — one function, `t` handed on as any value, `x is t` decided at run time by the rules of the literal test (758). A `comptime` parameter may still accept a value or a type where cardume's hooks need it (297, in 575 (5)'s spelling `comptime source: Atom<T> | type<T>`, the body testing `source is type<T>` — 736).

(2) **The tree rule.** A tree — an executor, a meta value, a member, a template's return — holds exactly run-time code (names resolved where written, 384), `syntax` (spliced as the expression held) and `comptime` (parameters and the body's `val`s, spliced as literals); a `compiler.*` call inside one is evaluated at build and spliced as its answer, in every tree, `syntax-captures-build` gone (575 (4), 614, 642); what the build knows always flows into run-time code and only the reverse is impossible: a `comptime` parameter of `Compiler` given a value the tree computes at run time is `compiler-arg-at-run-time`, at the argument, naming the parameter and the value (614, 642). A `syntax` splice is a `Syntax(e)` node, typed where the splice stands (638).

(3) **Expansion at the call.** A function whose body reads a `comptime` parameter and whose every parameter is `comptime` is expanded at its call site: what depends on build data runs at build, each statement that reaches a run-time value is emitted there as run-time code, once per iteration of a build loop, the build-known parts as constants; a loop bound or a condition needing a run-time value is refused at it; a function that also declares a run-time parameter is never expanded (562, 581). A caller's argument that breaks an expanded body is refused at the caller's argument (695). A function whose parameter is `syntax` is expanded at its call: `syntax q: string` takes a template text `` @`…` `` (578); a `syntax` parameter of any other type takes an expression written between the parentheses of an ordinary call — `snap.matches(render(page))` with `pub fn matches(syntax value: unknown) -> anyvalue { val at = compiler.source(value); return code @`snap.matchesAt(${value}, ${at})`; }` — and the body is a build body returning the code that stands at the call (719); `compiler.source(value)` is the call's `Source(file, line, col)`, `file` the file relative to the package root as diagnostics print it (`src/main.bp`), never the module path (756). A `syntax q: string` parameter still takes only a template text — `markup("…")` with parentheses is `syntax-call-outside-syntax` — and a decorator's `syntax decl` stays the annotation's (575 (4), 716, 719). The explicit argument `comptime compiler.src()` is an ordinary parameter and stays valid (718, 719).

(4) **Building types and code.** Any function declared `-> anytype` builds a type: a module-level `val X = f(…)` whose callee answers `anytype` is evaluated at build and `X` is a type, the callee resolved through the import graph, the checker keeping no list of std names; such a function has only `comptime` parameters; a `-> anytype` call anywhere but a module-level `val`'s initializer is `anytype-outside-type-val` (670). `anyvalue` is written only as the return of a template or of a function with a `syntax` parameter expanded at its call, or as `compiler.ast`'s answer, `anyvalue-outside-template` elsewhere (578 (4), 719).

(5) **`comptime` expressions and blocks.** `comptime <expr>` is `comptime { <expr> }` (255 (2), 525); a `comptime` is evaluated at compile time everywhere, calls, loops and records included, on the one comptime runtime, and its value is lifted into the emitted program — a literal as a literal, a record or a collection as its construction, a reference to a top-level function as that reference; a lambda capturing state and a resource stay `comptime-value-not-liftable` (266, 331). A block used as a value answers its last expression written without `;`; `comptime { break v; }` is gone (525). `comptime` is the one crossing from run-time code into the build, `compiler.init` the one crossing from a build body into the program; there is no `runtime` keyword (632). ## stages-and-folding — `Build`, `Run`, `Any`, and what is computed at build

**Every function has a stage computed from the resources it names; what depends on nothing of the run time is computed at build wherever it is written, fully or an error at build.**

(1) **Resources and propagation.** Build-only: `compiler` itself — `compiler.*`, a template body's reads (376 (1), 634 → 575 (3)). Run-only: a host function with an effect (io, `fs`, clock, random, network, `process`, `env`), an `await` on a host `Async`, a module `var` (376 (1), 547 (iv)). Neither: arithmetic, strings, records, arrays, `case`, loops, std's pure primitives — `Any` (376 (1)). `Any + Any = Any`, `Any + Build = Build`, `Any + Run = Run`; `Build + Run` is `build-and-run` at the second resource, naming the first; a `comptime { … }` block inside a `Run` function is resolved at build into a constant (376 (2)). Host functions are `Run` by default; std declares `Any` on its pure primitives (376 (4)); a function's stage is written only as `#[stage(.Any)]`, `stage` imported from the std module that owns it; `Build` and `Run` are never written — `#[stage(.Build)]` / `#[stage(.Run)]` refused by `stage` itself (681, 663). `use` is a means, not a stage: `use h(…)` has `h`'s stage — `provide` and `context` are `Any`, `request()` / `response()` / an atom `Run` (376 (3)). A body that runs at build calls `Build` and `Any` functions, never a `Run` one — `run-in-build` at the call (376 (5)). A call's stage is the called declaration's, and only what is written at the call counts — a call through a function value, a method on a value, a lambda received add nothing; `val f = clock.now; f()` passes the checker and is refused when the build executes it and reaches `clock.now`, the build's runtime raising `run-in-build` at that call, located (720). In a function whose every parameter is `comptime`, reading one no longer makes it `Build`; it makes it expanded (562, amends 376 (1)). The stage is published with the hooks list (`HookNode.stage`) (376 (6), 277).

(2) **Folding.** An expression whose every input is known at build (a literal, a constant `val` of any module, a `comptime` value, a context read known at build) and whose every function is `Any` is computed by the comptime runtime wherever it is written — a body, an argument, a hole, a `val` —, no `comptime` needed: `val raio = ESPACO * 2 + 4;` inside a component is `12`; `padAll(n)` with `n` a parameter is not (380 (1)); a `Build` read in a run-time body is written under `comptime` — `compiler` there without it is `compiler-at-run-time` (575 (3), 606 (3), 607 (1), 634). An `Any` function that writes no `panic` / `throw`, no `print`, no module `var`, no function-value call and no method of a declared type folds, and its calls through other such functions fold too (682); `print` is an effect and never folds (632). No limit: what runs at build runs to its end — no step or time budget, no fallback to the run time; a computation that never ends never ends the build (380 (2)). Every raise met while folding is a build error at the expression — a failed conversion, a missing key, a `panic` reached inside an `Any` function; an index out of bounds is no raise, `xs[3]` answering `null` (777) —, the message the target would print; this lands after the comptime runtime's primitives answer exactly as the targets do (721, 380 (2)). A raise written as such — `panic(…)`, `throw` — is never computed at build unless `comptime` is written: a dead branch's `panic("never happens")` stays a run-time raise (380 (3)). `comptime` written demands the build: an input of the run time under it is an error at the input (380 (4)).

(3) **Arithmetic at build.** An arithmetic error at build reads as Erlang's, located as JavaScript's: `` error: comptime-badarith: an error occurred when evaluating an arithmetic expression — `1.0 / 0.0` (division by zero) `` with ` --> src/main.bp:<line>:<column>` (472); every division and remainder by zero — `/` and `%`, integer and float, alone or inside a larger expression — reads `… (division by zero)`, located at the operator that divides (533). Structural equality at build answers whatever the depth — iterative, never bounded by the runtime's stack; a depth limit is never part of the language's answer (471). A raise at build is located at the call that raised, in its own file, every call of the chain a `called from <file>:<line>:<column>` line, innermost first, down to the program's call, annotation or `comptime`; a call inside a template expansion takes the frame of the template's use (532).

(4) **Components at build:** a component may be called at build — in a `comptime` block, a template, a module `val` known at build — when its stage is `Build` or `Any`: it runs on the comptime runtime with `RenderScope.root()`, its contexts answering their providers within the tree or their defaults; one reaching a `Run` hook is `run-in-build` at the call (378 (4), 388 (4), 594 (1)). A `styled` literal is computed at build when every hole is known at build, at render only when a hole is not (355, 377 — § styling).

## decorators — a decorator is a function over the annotated declaration

**A decorator is always a function whose first parameter is `syntax decl`; its name at build is a declaration handle; each invocation is independent; a tag's annotation and a declaration's decorator are one thing.**

(1) **The form.** `#[name(…)]` names a function whose first parameter is `syntax decl`; no type or enum is an annotation by implementing a behavior — `Annotation` is gone; the data an annotation carries is a record the decorator records with `compiler.setMeta` (`pub fn mark(syntax decl: unknown, comptime label: string) -> void { compiler.setMeta(Mark(label: label)); }`, `#[mark(label: "x")]`); the enums used as keys follow: `#[stage(.Any)]`, `#[beamMemory(.Ets)]` (663). There is no `Decorator` type: a decorator's name at build is a declaration handle, two compared with `compiler.same(a, b)`; `DeclAnnotation(decorator: unknown)` (666). A marker is a decorator with an empty body, `pub fn page(syntax decl: unknown) -> void {}`; `declare fn page(syntax decl: unknown);` is refused `declare-without-implementation` (604). A decorator's other parameters are `comptime` or `syntax`; an argument may be of any type — a function, a type, a `compiler.Field<T>`, an enum, a record — checked at the argument; `.Name` resolves exactly as declared, case included, no output converting case (280 (1), (4)). A default is trailing, decorators included (244, 406). Both annotation forms are valid and printed as written: `#[a]` then `#[b]`, or `#[a, b]`; meaning identical, each item its own annotation in written order (286). A decorator reached through a namespace import runs, whatever module declares it — `#[ns.d]` is `#[d]` imported by name; an annotation is never accepted and not run (386). No module-level annotation: `#![…]` stays a parse error, an annotation always annotates the declaration that follows (315). A name after `#[` that is no decorator is B-145's refusal (663).

(2) **The handle.** The declared type of `syntax decl` is the contract the annotated declaration must meet: `syntax decl: unknown` admits any declaration and gives `decl` no member (`decl.make` is the checker's own `unknown has no member`); `syntax decl: Module` (a behavior) admits a type that implements it — one without `implement Module` refused at the annotation, located, naming the type and the behavior —; `syntax decl: fn(…) -> R` admits a function, `decl(…)` callable; `syntax decl: T` keeps the type; the check is structural, against the members the behavior lists (716 (1), 626 (2)). Inside every tree the decorator writes — an `init` executor, an `addMember` member, in a type position too — `decl` is the annotated declaration itself as code, bound to that declaration, never "what the name resolves to in the module": a `fn` is the function value, a `val` its value, a type the type in expression position (`decl.make()` is `Users.make()`, `decl(repo)` its constructor), a method `Users.make` by its owner's path, a behavior the behavior name, a field its owner's field; `-> decl` is the annotated type or behavior (613, 626 (1), 627, 716 (3)). The decorator's body and its trees are type-checked once, at the decorator, against the parameter's type; an annotation is checked only against the contract; no error surfaces inside an executor with a `called from` line (716 (2)). A member's handle names its owner, `compiler.owner(d)`, `null` at module level (526, 576 (3)); a method-level decorator sees its own method — name, parameters, return type, module — and the type-level decorator reads the type and every method with its annotations; a method marker is placement (347). Inside a decorator, `compiler.meta<T>(decl)` on its own handle is refused — a declaration's meta is read by the code that consumes it, after every annotation ran; a `compiler.*` read inside the decorator's `init` executor is folded after every annotation of the declaration ran, so `compiler.meta<Entity>(decl)` there is allowed (680). A decorator never reads a body (655 → 576 (8)).

(3) **Independence and order.** Each invocation is independent: a decorator's answer depends on its declaration alone; a module `var` written by a decorator body stays refused (343). The order decorators run in never changes an answer (347). Provisional: a decorator that reads `compiler.hooks(d)` runs last in its module and only records meta or refuses — `addMember`, `addType` in it `decorator-hooks-output` (372, 576 (8), 725). A same-module typed meta read of its target is 592 (5)'s: the meta of a block is filled after its decorators ran, and a read needed before them is the located `dependency loop` (592 (5), (6), 728; 419 replaced). A duplicate across declarations — two `#[provides]` of one type, two handlers of one route — is the registering executor's refusal at init, before `main`, naming both (665, 343 as amended).

(4) **Errors in added code.** A type error inside code a decorator added is located at the annotation that added it, the message naming the member or associated type by its owner's path and the decorator's `addMember` / `addType` call with its file and line (567). A second `addMember("validate", …)` on one declaration is `decorator-member-duplicate` at the second annotation; several annotations reach one member through typed meta (404, 216). A decorator's per-function code is generic library code fed by meta: `#[page]` records its route in typed meta and a page reads its segments with `use params<P>()` (236).

(5) **Tags.** A tag's annotation and a declaration's decorator are one thing: on a tag, `compiler.kind(decl)` is `Element` or `Component` (`compiler.component(decl)` the component's own handle, the tag's name and static attributes readable), and the channel is typed meta — the annotation records, the template function reads it back by type; `addMember` / `addType` on a tag refused; the meta types `Hydrate`, `Defer`, `RawBody`, the transition metas, `isInline`'s style meta, `LinkReload`, `LinkHistory`, `ClassName(names: string[])`, `StyledMeta`; one `setMeta` per type per tag, `addMeta` repeats; a template function building a tag's handle and reading its meta is generic compiler surface (302, 576 (3)). A template body builds a tag's handle with `compiler.tagDecl(kind, name, syntax attrs)` and runs its annotation through `compiler.annotate(d, at: Span)`; the annotation's text is read from the span, never passed as a string (636). Outside markup, expression-level work is a call; a tag's annotation is the one expression-position decorator, `val x = #[deco] 1;` refused (705). A handle `compiler.bindings(e)` answers has no read of the decorator that annotated it; a template body tells annotations apart by the meta they recorded (679).

(6) **Where a decorator is declared:** only in `src/comptime/`, in std or in a dependency (592 (3)). No `@emit`, no `@code`, no `@expr` (605, 575 (8)): a registration is an `init` executor, a generated type a template text handed to `addType`, a generated function a typed `addMember`, a generated helper beside a `fn` a run-time helper of the library (605 (1)–(4)). `compiler.wrapWith` is gone: a decorator never changes what a call does without the caller seeing it; behaviour around a type's methods is a proxy type the decorator builds (`OrderService.Tx`), around one function a function written around the call (`retry(policy, { -> issue() })`) (714).

## decorator-outputs-and-meta — members, associated types and typed meta

**A decorator produces typed meta, a typed member and an associated type — each under the type's path, never a free module-level name, never source text — and a name resolves where it was written.**

(1) **The places.** A decorator writes only under a type's path: a member (`Account.validate`), an associated type (`City.Columns`), typed meta; never a free module-level name, no `@emit` (216, 373, 575 (3)). The outputs are `compiler`'s, a decorator's only (`compiler-output-outside-decorator`): `setMeta<M>(syntax value: M)` (one per `M` per declaration, a second `decorator-meta-twice`), `addMeta<M>(syntax value: M)` (appends what repeats; one type is set or added, never both), `addMember<F>(name, syntax member: F)` — the typed form, the only one; the string form is gone —, `addType(name, syntax source: anytype)` — written code; the typed `compiler.addType(name, compiler.buildType(…))` replaces the string `addType(name, source)` (298, 418, 575 (3), 576 (9), (14), 578 (3), 640 (2)). A decorator adds and never merges or replaces: a second `addMember` of one name on one declaration is `decorator-member-duplicate` at the second annotation; several annotations reach one member through typed meta (216, 404). `compiler-output-outside-decorator` does not reach a built type's members: a build body may build a type and give it members, `addMember(M, name, member)` with the target first (644).

(2) **Typed meta.** `compiler.setMeta(Entity(table: "cities"))` stores one value per type per declaration, `addMeta(Index(…))` appends; read `compiler.typeInfo(City).meta(Entity)` → `?Entity`, `.metaAll(Index)` → `Index[]`, `compiler.meta<M>(d)` → `?M` / `compiler.metaAll<M>(d)` → `M[]` on a handle (727); the key is the record's type, not the decorator's name: a renamed decorator changes no reader, two decorators may write one type, one decorator several, and who may read is who sees the type (298, 576 (11)). `meta(T)` over several values is `typeinfo-meta-several`, read with `metaAll`; `metaAll(T)` answers a set-once value as a one-element array (418). The string meta is gone: `setMeta(key, value)` and `.meta.<decorator>.<key>` removed; one spelling (576 (11)). A meta record's field that holds code is written `T` and holds a tree when filled from a `syntax` (576 (12), 370 (1) as carried). A meta field holding code (written `T`, filled from a `syntax`) read in another module resolves its names where the annotation wrote them — bound under an alias no source can spell, a private one travelling as a template's private does; a same-named function of the reader is never captured (385). A generic meta record is read through `compiler.typeInfo(X).metaAll(Check)` (420, 698). A field's decorator records no meta; string meta on a method stays refused (697). **When meta is read.** A block's meta is filled after its decorators ran; a read needed before them is the located `dependency loop` (592 (5), (6), 728). Inside a decorator `compiler.meta<T>(decl)` on its own handle is refused: a declaration's meta is read by the code that consumes it, after every annotation ran — a run-time body under `comptime`, a template body, or the decorator's own `compiler.init` executor, folded after every annotation of the declaration ran; annotations never depend on their order (680, 728).

(3) **Members.** A member a library's decorator writes resolves each name where it was written: the library's names in the decorator's module, the annotation's arguments in the annotated module — 112's hygiene for members; the user imports nothing beyond the decorator; `decorator-member-fn-imported-name` goes (384, 669). A typed member reads its own type's typed meta through the decorator's type parameter, checked twice — pre-comptime in the decorator's body (`compiler.typeInfo(T).metaAll(Check)` typed `Check<T>[]`), post-comptime in the annotated type; the read is a resource of build, written under `comptime` in a run-time member; no `typeInfo(Self)`: the decorator's `T` names the annotated type (395). Inside a member the owner is `decl` (626 (1)); a `compiler.*` call inside a member — `compiler.addMember("label", fn() -> string { return compiler.name(decl); })` — is evaluated at build and spliced (`"Users"`); `compiler.name(x)` with `x` the member's parameter answers `"x"` at build; `decorator-member-captures` is gone (642, 716 (3); replaces 413); a body local whose value is no literal read inside an added member or an executor is `decorator-member-local-not-literal`, located at the read (759, 575 (4)). A `behavior` takes a static member through `addMember` as a type does, and inside an added member `decl` names the owner in a type position too — `fn() -> decl` (627). Code a decorator writes resolves in the decorator's module, a type it builds included — `Field("clock", Clock)` names that module's `Clock` whether or not the annotated module imports it; what the user writes in the annotation resolves in the annotation's module; reaching the caller's scope by name is `compiler.lookup` alone (669). A decorator hands a parameter's code on only through the typed channels — typed meta or a typed member — never source text spliced into a string output (370, 281). No code identifier passes as a string: a function, a type, a field, an enum variant, an event, a hook or an action is referred to by the thing itself — a function value, a `type`, a `compiler.Field<T>` / `.name`, a variant — checked where it is written; a name that belongs to another system stays a string — an SQL table or column, a URL or route pattern, a cache name, an Erlang function, a config path, a wire spelling, text for a user (281).

(4) **Associated types.** `addType("Columns", type(id: string))` — written code (640 (2)); a type declared in the body of a type is that type's associated type (330 (7)); `City.Columns`, `Mailer.Mock` reach every importer (216). A generated type is a template text `` @`…` `` answering a type handed to `addType` (605 (2)).

## derived-types-and-fields — `Type.*`, `compiler.Field<T>` and `compiler.Info<T>`

**A derived type is an inline type named by its `val`, built by a botopink body over `compiler.fields` and `compiler.buildTypeInline`; a field's default travels with it; `compiler.Field<T>` is a build-time value with a run-time form.**

(1) **The five utilities.** `import {types.Type} from "std";` then `pub val RecipeTitle = Type.pick(Recipe, .title);`, `Type.partial(Recipe)`, `Type.omit(Recipe, .description)`, `Type.merge(Dog, Breed)`, `Type.required(T)` — statics of `Type` in `types.bp`, written in botopink over `compiler.fields(T)` and `compiler.buildTypeInline(fields)`, every parameter `comptime`, run only at compile time, no `comptime` keyword at the call (307, 599 (3), 629, 630, 628). A derived type is an inline type named by its `val` — `pub val Patch = Type.partial(Pessoa);` is `pub val Patch = type(nome: ?string, idade: ?i32, email: ?string);` —, usable in every type position, exported and imported like any type, annotatable (`#[validated] pub val RecipePatch = Type.partial(Recipe);`); there is no lineage and a spread is typed by structure: `Pessoa(..nome, idade: 3)` with `nome: Nome` accepted when the fields match, `Pessoa(..patch)` refused at the `..` because `?string` is not `string`; two structural types with the same fields are one type (629; amends 600's nominal reading and 359 (2)). An inline type bound to a `val` is named by that `val` wherever a type is named; `inline-type-outside-parameter` stays for a `type(…)` literal in a field, a return or an annotation — the literal lives in a parameter or in a `val`'s initializer (629 (2), 207); an inline type may `implement` a behavior, a `val` bound to one is that type's name (645). Any function declared `-> anytype` builds a type the same way; std's five are the first of them, not a privilege; such a function has only `comptime` parameters, a run-time argument `comptime-arg-not-known`, and a `-> anytype` call anywhere but a module-level `val`'s initializer is refused at the call, `anytype-outside-type-val` (670). `derived-type-outside-val`, `derived-type-cycle`, `record-field-duplicate` hold over the built type (307, 578 (3)). A plain alias (`type Id = i32`) stays transparent (307). `Type.required` takes the `?` off each field and drops a `null` default with it (`description: ?string = null` → `description: string`); any other default stays and travels (422, 699, 671). A derived type carries the fields and their annotations only — no methods, `implement` clauses or type-level annotations of the source; the `val`'s own annotations go on the type (423, 700, 629). A generic record or an imported alias is not a source — `derived-type-source-not-record`; a local alias of a record is that record (424, 701). validation's `#[pick]`, `#[omit]`, `#[partial]`, `#[required]`, `#[extending]` are gone (307).

(3) **`compiler.Field<T>`.** A build-time value: the fields of `T`'s declaration, `.field` written where a `compiler.Field<T>` is expected in a decorator's argument (`#[index(.state)]`), checked against `T`'s fields; the run-time key is gone — `Type.keys`, `Field.of`, `Field.all`, a key matched by `case` (599 (1), (2); amends 308). It has a run-time form, its constructor over the owner type and the name: a `comptime` whose value holds a field splices `Field(Book, "pages")`, which prints, compares (`≠ Field(Author, "pages")` by the owner) and keys a `Dict`, `.name` → `"pages"`; `type`, `annotations` and `defaultValue` are build members, refused in a run-time body (`` `annotations` is a build member of `Field` ``) (631). The rule from here on: a type or a value assembled at comptime is assembled by a botopink body over `compiler.*` — `compiler.fields(T)` to read, `compiler.buildType` / `buildTypeInline` to build, `addType` / `addMember` to attach — never by a compiler-side special case; `comptime/derived_types.zig` keeps only the record's materialisation and the two `val` rules (599 (3), 575 (7)). The builders take a structure, `compiler.Field<unknown>[]`, never record text (625 (3), 629 (1)); `buildType(name, fields, implements)` answers a nominal type, `buildTypeInline(fields, implements)` the structural one (629 (1), 645). B-149 owns the builders' surface and `mocks.bp`, B-140 `Type`'s bodies and `compiler.fields` (640 (1)).

(4) **Spread and derived types:** a spread copies field values by name and type from any record whose fields match the target's (629 (3)); a derived type's value is built by its own name (600 as carried); nothing of the source's behaviour travels (715) — § records-and-props.

(5) **`compiler.Info<T>`.** `compiler.typeInfo<T>(comptime t: type<T>) -> compiler.Info<T>`: the record once `TypeInfo<T>` is `compiler.Info<T>`, declared in `compiler.bp` beside `compiler.Field<T>`; both are imported where named (`import {compiler.Field} from "std";`), while `Type` and its statics stay in `types.bp`, which imports `compiler` (606 (3), 630). ## templates — `name @`…``, template methods and annotations, holes and types

**A template is a function whose first parameter is `syntax q: string`, called one way — its name before a raw template text `` @`…` `` —, returning an ordinary type, `anyvalue` or `anytype`; the code it answers is built, never parsed back from a string.**

(1) **The call.** The template text `` @`…` `` is a token of its own: it may span lines, holds its bytes as written — no escape sequences but `` \` `` for a backtick, no interpolation —; `${…}` and `{…}` inside it are the sub-language's own syntax, parsed by the template from its raw text; a hole's expression is spliced into the code the template answers and typed in the caller's scope — the template never reads its value (577 (1)). A template is called only as `` name @`…` `` — in run-time code or inside a tree —, `` recv.name @`…` `` (a template method, `syntax self: R` first), or as an annotation `` #[name @`…`] `` (the second `syntax` parameter the annotated declaration); `name "…"`, `name("lit")`, `name<T>(…)`, `#[name(…)]` and the template taken as a value are `syntax-call-outside-syntax` (577 (3), 578 (1)). That is the `syntax q: string` parameter's rule: a function whose `syntax` parameter has any other type takes an expression written between the parentheses of an ordinary call — `snap.matches(render(page))` with `pub fn matches(syntax value: unknown) -> anyvalue` — and is expanded at the call, its build body reading the expression through `compiler.*` and returning the code that stands there; `markup("…")` with a `syntax q: string` stays `syntax-call-outside-syntax` (719, amending 578 (1)). A template declared with any other parameters is `template-signature` (577 (4)). A template function is an annotation only when its signature declares the annotated declaration as its second parameter; called as `` f @`…` `` it is `template-annotation-only`, and a template without that parameter at `` #[f @`…`] `` is `template-annotation-without-decl` — the two uses are two functions (696, 311 (2)). A template method is found by a name in the call site's scope — `` value.method @`…` `` resolves `method` as a template whose `syntax self: R` takes the receiver; a receiver's type never imports code by itself (685, 311 (3)). A template call expands wherever an expression may stand — a method body, a destructuring initializer, a lambda, an argument, a field default, a `case` arm; one left unexpanded is a compiler error, never a run-time `undefined` (425).

(2) **The return and its type.** A template returns an ordinary type `T` (the type of the code it answers), `anyvalue` (the call takes the built code's type, checked where the call stands) or `anytype` (the call is a type, built); there is no `-> syntax T` and no `-> expr` (578 (1), (2)). What a call becomes is the template's return value, a tree: any returned expression is captured and spliced as written (578 (3)). A template call's type is the type of the code it built for that call, computed at build; the signature's answer is a bound the built type must fit, an error in the template otherwise; the call unifies with the expected type as any expression — `val n: i32 = query @`…`` is `expected i32, got Array<string>` at the call; `compiler.note(message)` attaches the template's reason to the mismatch line as `— note: …`; the template never reads the expected type, so what it builds is decided by its text (426, 686). A template answering a custom tree for the language server attaches it with `compiler.custom(ast: CustomNode)` (576 (4)).

(3) **What a template body reads.** The text with `compiler.text(q)` (raw; no `Part`, no `compiler.parts` — no hole is the language's) (577 (5), 578 (5)); the caller's `${…}` holes as `syntax` values with `compiler.holes(t)`, the i-th the i-th hole's expression, opaque, typed in the caller's scope when spliced (637); a name of the call site with `compiler.lookup(e, name)`, answering an opaque declaration handle, `null` when nothing of that name is in scope, read-only (`setMeta` / `addMember` on it refused), its data meta readable at build; the read declaration's decorators run before the template body (415 (2), (3), 576 (3), 669); `compiler.bindings(e)` — only the bindings whose name appears as a word in the captured text; a `lookup` of a name that is not a word of the text is a located comptime error (237, 686; `ctr:` 577 (5) amends 237 where it reads a language hole, and the word rule still bounds `lookup` / `bindings` — 731 (5)); `compiler.source(e)` the call's `Source(file, line, col)`, `compiler.context(e)` (576 (2), 719). A template body builds a tag's handle and runs its annotation through `compiler.tagDecl` / `compiler.annotate` (636). The library decides which types an embedded expression may have: the template accepts or refuses it with a located comptime error; the compiler fixes no list (190). A template hole writes `print`'s text for every value — a record, an array, a tuple, `null`, an enum; a string writes itself; a type implementing std's `behavior Display` (27) writes its `display()`; a `bytes` hole stays refused, a `?T` hole of a `rakun-bpp` template stays an error (530, 520, 204). The code a template builds resolves each name where it was written: the library's text in the template's module, private names included, carrying their identity; the caller's holes and words at the call site; `compiler.lookup` answers the declaration and never an alias (112, 669).

(4) **Where built code is located.** Every loc-keyed plan is keyed by (expansion id, offset); a module with two alike expansions needs no padding; `query`'s `query.bp` and `rakun-bpp`'s `html.bp` drop their padding when it lands (429). An error in template-built code is located by the word it copies from the template text (the first occurrence after the previous match); a sub-language records nothing for it (691). A call inside a template expansion takes the frame of the template's use (532).

(5) **Migration.** The codemod rewrites `name "…"` / `name """…"""` / `name("lit")` / `#[name("lit")]` → `` name @`…` `` / `` #[name @`…`] `` with the string's escapes resolved to raw bytes; `-> @Expr<T>` / `-> @ExprCustom<T>` → `-> T`; `@expr(v)` → `v`; a bare type-position `type` → `anytype` (577 (6), 578 (5)).

## functions-lambdas-and-blocks — typing, tails, `defer`, variadics, defaults

**Every function is typed where it is written; a `{` without `->` is a block and never a closure; a body's last expression written without `;` is its value.**

(1) **Typed where written.** Every function writes its return type, `-> void` included: `fn m(self: Self) -> void { … }`, `pub fn main() -> void { … }`; a `fn` with no `->` is refused at its name, `fn-return-missing`, `write -> void, or the type it answers`; no inference of a function's type from its body remains; applies to a method, a `default fn`, a `declare fn`, a static, the typed lambda `fn(x: T) -> R { … }`, a `.bpp`'s functions (622, 33; removes 06 C9 and 328's inference). A lambda `{ x -> … }` declares no types — `{ n: f64 -> n }` stays a parse error — and is legal only where its position fixes its type: the parameter it is passed to, an annotated `val`, a typed return; a lambda nothing types is `lambda-untyped`, located (`nothing types this lambda — write fn(n: T) -> R { … } or type the val`); inference from later calls is gone (583, 328 as amended). A lambda's return is its expected type's: under `fn(x: T)` a `try` in the lambda is `effect-try-without-fallible-channel`; a lambda that can fail is written under `fn(x: T) -> Result<U, E>` (147). The typed function expression `fn(x: T, …) -> R { … }` is legal in every position — a `val`, a `var`, an argument, a return, `addMember` —, every parameter typed or none; where the position has a type the written types are checked against it (408). A free type variable as the expected return accepts the typed forms' own marker, and an expected type that is no function type is left to ordinary unification — both as built until B-116 P4's codemod has run, then refused (712).

(2) **Tails and blocks.** A body's last expression written without `;` is its value — a named `fn`, a method, a `fn` expression, a lambda: `fn inc(x: i32) -> i32 { x + 1 }`; with `;` it is a statement and a `-> R` body then needs a `return`; a valued tail or a valued `return` in a `-> void` body is refused at it; an early `return` stays; a braced block statement at the end (`if` / `case` / loop) is not the tail; the formatter neither adds nor removes the tail's missing `;` (409, 622, 541 (1)). A `{` followed by parameters and `->` (or `->` alone) is a lambda; a `{` without `->` is a block — a scope, never a closure; a trailing lambda with no parameter writes `f(x) { -> … }`; `@block` is removed; a block used as a value answers its last expression written without `;` — a bare `{ … }`, a `case` arm `p { … }`, `comptime { … }`, `async { … }` alike; a `return` in a block leaves the enclosing function, a `return` in `async { … }` leaves the `async` block; a `var` reassigned in a block is a plain reassignment; a block handed where a function is expected is refused with the hint "missing `->`?"; a block whose value is `void` handed where `unknown` is expected is refused (525). `await`, `yield`, `break` / `continue` to an outer loop inside a block reach the enclosing function or loop; a `case` arm's `break <value>` is removed, the arm's value its tail; a block as the last statement of a function body is its tail (541 (2)–(4)). `if` is not an operand, parentheses included: `val x = if (c) { a } else { b };` (159). A braced `if`, loop or `case` statement ends at its `}` (29); the `;` after it is accepted by the parser and removed by the formatter (524, 60); a braceless statement keeps its `;` (60).

(3) **`defer`.** `defer <expr>;` runs `<expr>` when the block it is written in ends — block scope, as Zig and Swift —; several run in reverse order; it runs on every exit (the end, `return`, `break`, `continue`, a propagating `try`, a `throw`, a panic `attempt` catches); in an `async` body when the task's body ends, after its awaits; in an `AsyncIter` when the stream ends or its consumer stops; its body cannot leave the path (`return`, `break` / `continue` out of it, `yield`, `await` refused); the deferred expression is evaluated when it runs, not when `defer` is written (`var f = open("a"); defer f.close(); f = open("b");` closes `b`), and a `return <expr>`'s value is computed before the block's defers run; no resource check: a `Closeable` value not closed compiles; std declares `pub behavior Closeable { fn close(self: Self); }`, known to no compiler rule (539). A `defer` always runs on every target, whatever goes wrong: a function holding one adds `.exceptions` to the program's `needs`; `defer f.close(); print("x"); panic("y")` answers `x`, runs `f.close()`, then aborts (597).

(4) **Parameters.** A variadic parameter is spelled by the declaration, `..values: unknown[]` — only the last parameter, at most one, its type an array, no default and no label; a call passes zero or more positional arguments after the fixed ones; no spread at the call site (an existing array is passed by declaring `values: T[]`); commonJS a rest parameter, erlang / beam one list, wasm one array (267). A default is trailing everywhere — free `fn`, method, record fields and variant payload alike, decorators included (`fn-param-default-trailing-only`) (244, 406). A second binding of one name in one body is `binding-redeclared` at the second, naming the first, parameters included, reaching every block and every `case` arm; two sibling blocks may each bind the same name; no target invents a scope (152, 205). A plain function call takes no spread; a record constructor does (359, 529 — § records-and-props). An integer literal past its type's range is refused by the checker (319). Assigning to a `val`, local or module-level, is a located error naming `var` (38).

(5) **Precedence.** `await` and `try` are prefix operators binding as the unary `-` does (`await t * 2` is `(await t) * 2`); postfix (`.`, `()`, `[]`) binds tighter (`await t.x` is `await (t.x)`); `catch` is an infix operator with `??`'s precedence, below every arithmetic, comparison and logical operator, its left side the whole expression before it; parentheses group as anywhere (537). `??` beside `&&` / `||` without parentheses is a compile error (330 (4)). A type name with explicit type arguments followed by `.member` or `(` is a type application (`Dict<string, unknown>.empty()`); elsewhere `<` is a comparison (255 (1)). A call's result may be called (`adder(3)(4)`), a parenthesised expression takes a member (`(a == b).toString()`), and any type takes `[]` — `#(a: i32, b: string)[]`, `Result<…>[]`, `(i32 | string)[]` (28, 14).

(6) **Loops.** `loop`, `while` and `for` are statements (`void`), one meaning each — `loop { … }` repeats until `break`, `while (cond)` while its condition holds, `for` over a collection, a range or an iterator —; `continue` exists in all three; a label follows the keyword, named by `break :outer` / `continue :outer`; a `break` with a value, `yield` and a collecting loop exist only in the `iter` / `async iter` forms of § body-markers-async-and-iter (105, 584, 553).

## body-markers-async-and-iter — `async`, `iter`, `component`; `Async<T>`, `Iter<T, R>`, `AsyncIter<T, R>`

**A body that compiles specially carries a marker; the return type is written whole, named after its marker; a task behaves as a Promise on every target; every composition of a task is an `async` block.**

(1) **Markers.** The markers, before `fn` and inside a lambda's brace: `iter` (`yield`), `async` (`await`), `async iter` (`yield` and `await`), `component` (`use`, `await`) — `pub async fn`, `iter fn() -> Iter<i32> { … }`, `{ async x -> … }`, `{ iter -> … }`, `{ component -> <div/> }` (553 (1), 584 (1)). A marked lambda's marker is written inside the brace, before the parameters; `async {` is always the block, `iter loop {` the loop, `{ async` / `{ iter` / `{ component` always a lambda; a marked lambda goes wherever a lambda goes, trailing included (584 (1)); its body is a function body — `return v` is the iterator's `R`, a top-level `continue` refused `continue-outside-loop`, `break v` refused (584 (2)). A declaration writes its annotations first, then `pub`, then `default`, then its marker, then `fn` — `#[serverAction] pub async fn count(…)`; any other order is a parse error at the marker (572). A marker is for a body: a bodyless function — a `declare fn`, a behavior's abstract member — writes its return type alone; a marker on one is `marker-on-declaration` (571). The keyword without its marker is refused under the marker's name: `await-without-async`, `yield-without-iter`, `use-without-component`, each hint naming the marker to write; `marker-without-arrow`, `marker-lambda-without-expected-type`, `marker-type-mismatch` stay; `iter-await` refuses an `await` in an `iter` body, the hint naming `async iter` (573, 553 (4)). `async fn f()` with no return type is `marker-type-mismatch`, "write `-> Async<…>`" (584 (3), 622).

(2) **The types.** The return type is written whole, named after its marker: `Iter<T, R = void>` and `AsyncIter<T, R = void>` (`T` each `yield`'s value, `R` the value the iteration ends with — the body's `return v`; `next()` answers `Step.Item(T)` or `Step.Done(R)`), `Async<T>`, `Component<R>`; `@Iterator`, `@Task`, `@Stream`, `@Component` are renamed, and `Task` is no name of the prelude — 606 (1)'s `Task<User>` and 623's `Task<…>` read `Async<…>` (732); a marker whose return type is not its type is `marker-type-mismatch` (553 (2)). Without a marker a body returns the whole type: `async fn load() -> Async<i32> { return 1 }` returns the value, wrapped; an unmarked `fn load() -> Async<i32>` returns an `Async<i32>` itself (`return Async.resolve(1)`), so `fn load() -> Async<i32> { return 1 }` is a type mismatch, the hint naming `async fn` and `Async.resolve`; the same for `Component<R>`; a caller sees no difference (570). A function that hands a value on writes the same signature with no marker; a component's asynchrony stays inferred (553 (5), 375), from its own body only — never because of its children: composing another component only puts its lambda in the tree, and the root is always asynchronous (725; § contexts-and-components (4)). `Iter<T, R>` declares the iterator helpers whole, typed, on every target — `map`, `filter`, `flatMap`, `take`, `drop`, `forEach`, `toArray`, `reduce`, `some`, `every`, `find`; a method outside the set is `unresolved_method` everywhere alike (596). A `component` lambda — `val c: () -> Component<Element> = { component -> … }` — compiles and runs as a `component fn` does, its captures carried, on every target (574).

(3) **Tasks.** `Async<T>` behaves as a Promise on every target: a task starts when it is made and runs to its first `await`; `await` suspends the awaiting body while other tasks run; a task settles once; `race` answers the first to settle, `raceOf` runs its thunks concurrently (392 (1), 654). `Async<Result<T, E>>` is the task that fails with `E`: its Promise rejects with `E` and resolves with `T`; `Async<T>` does not fail; `val u = try await buscar(1);` propagates, `try await buscar(1) catch User.guest()` handles, `val r = await buscar(1);` is a `Result`; erlang and beam end the task's process with `{error, E}`, wasm's scheduler settles it with the error; a crash in an `Async<T>` is a defect, contained by `attempt` (432). `map`, `then`, `mapError` and `catch` are withdrawn from tasks: a failing task is read only by `try await … catch` or `case` on `await`'s `Result`; composing without awaiting is an `async { … }` block, itself an `Async` whose value is its tail (`val safe = async { try await load() catch 0 };`) (523, 537 (3)). On wasm an asynchronous function is a resumable state machine driven by a scheduler over `wasi:io/poll` or the JS event loop — no JSPI, no WASI 0.3; a synchronous function pays nothing (392 (2), 504); the wasm backend binds each operand evaluated before an `await` in its statement to a frame local, so a call before an `await` runs once; until it lands the located refusal stays (505). A host adapter may answer `Async<T>` over a generic `T` — `#[compiler.external(.Wasm(wasi: .Delay))] pub declare fn delay<T>(millis: i32, value: T) -> Async<T>;` — its signature checked by shape at the annotation (393); one adapter list for both wasm hosts (394); B-25's gate adapters are `.GateNew`, `.GateOpen`, `.GateAwait` (690). Concurrency fixes results and the order of answers, never interleaving: `spawnAll` answers in input order, `race` the first to complete; no test depends on the order of effects (335 (2)); no cancellation in std's async — a losing racer and an expired timeout run to completion and their results are dropped (704). A module `var` whose type holds an `Async` is refused, located, on every target (547 (iii)). Unchanged: `async` exists only inside `Run` (376 (5)).

## result-and-failure — `Result<T, E>`, `try` / `catch` / `throw`, `attempt` and `Failure`

**`Result<T, E>` is botopink's checked error; `try` opens a region that `catch` closes; a failure is always a `Result` in the value's layer; a crash is contained by `attempt` alone, its `Failure` kind exact on every target.**

(1) **Checked.** `throw` and the propagating `try` need a `Result` in some layer of the return — `effect-try-without-fallible-channel`, its message naming `try … catch` and a binding's `result: true`; every call that may fail writes its `try` — no implicit propagation (`val x = try f();` propagates, `val r = f();` is a plain `Result`) (431 (1)). `Ok(…)` / `Error(…)` are never constructors in an expression: a `Result` is made only by `return v` or `throw e`; `Ok` / `Error` in an expression stay `unbound variable` (208). A failure is a `Result` in the value's layer on every type: `Result<T, E>`; `Async<Result<T, E>>`; `Iter<T, Result<V, E>>` / `AsyncIter<T, Result<V, E>>` — a `throw` or a propagating `try` ends the iteration with `Error(e)`, the items bare `T`, consumed by `for x in try xs` / `for await x in try xs`; `Component<Result<R, E>>` — a component throws only under it, the `Error` reaching the nearest `ErrorBoundary`; `return v` is `Ok(v)` where the layer is a `Result`; `Iter<Result<T, E>>` stays an iterator of results; `Result` needs no marker (553 (3)). `?T` is read with TypeScript's operators and has no methods: `??`, `?.`, `?.[i]`, `?.(args)` and the postfix `!` are the whole surface; `map`, `flatMap`, `unwrapOr` stay on `Result` (`r.map(f)`, `r.flatMap(f)`, `r.unwrapOr(x)`, `r.isOk()`, `r.isError()`, the one spelling; the builtin `result` namespace is gone); an operator over a value that is never `null` is a compile error; `?.` flattens; `x!` is checked at run time — a `null` aborts, alike on every target, with the location and the expression, a program error like `panic` (330; printed as every panic is, `panic: value is null — nome! at main.bp:3:13` — 492, 535, 731 (1)). `Result`'s declaration and value shape are § prelude-and-primitives (609). `Result<void, E>` is real — an assertion answers it with a bare `return;` in the `Ok` position — and a test body is a fallible context in which a propagated error fails the test (74).

(2) **Regions.** `try` opens a region; `catch` closes it and handles the failure of every `try` written in it: the region is the block `try { … }` when written, else the whole expression left of the `catch` — `(try a) + (try b) catch 0` sends both failures to the one `catch` (595 (1), (2)). The handler is an expression (the fallback), a `throw` (`catch throw ParseFailed`), a block whose value is the fallback, or a block with a binder `catch { e -> … }` — a `case` arm's binder, typed by the region (595 (3), 656). The region is an expression whose value is its last expression without `;`; an empty handler `catch { }` is `catch-empty` — a failure is handled or left to propagate, never swallowed in silence; a `void` region's handler is a block with at least one statement (595 (4)). One `E` per region: a second error type is `try-region-errors-differ` at that `try`, naming both — handle one on the spot or convert it (`catch throw …`) (595 (5)). A `try` in the handler's body belongs to the enclosing region or the function (595 (6)); a region holding no `try` is `try-region-cannot-fail` (595 (7)). Lowering: one early-exit block per region on each target — commonJS a labelled block or a sentinel, erlang / beam `try … catch` over a term of its own, wasm `block … br`; no new exception on wasm (595 (9)). Precedence: 537 (§ functions-lambdas-and-blocks (5)).

(3) **Crashes and `attempt`.** `panic` and an unannounced host raise are defects, never in a signature; `import {failure.attempt, failure.Failure} from "std"; val r = attempt({ -> plugin(x) });` answers `Result<T, Failure>`, the one way to contain one; `attempt` alone catches `panic` / `crash`, `catch` only a `Result`'s failure (431 (3), 595 (8)). `attemptTask(f: fn() -> Async<T>) -> Async<Result<T, Failure>>` is `attempt`'s task form (494); `asserts.throws<T>(body: fn() -> T)` is generic, over `attempt` (493). `Failure`'s kinds, exact on every target: `panic` — `panic(…)`, `x!`, an overflow, a division by zero (integer, and float on erlang and beam), a failing `assert` (`assertion failed: x > 0 at src/main.bp:12:5`, with the program's message when given); `host` — a raise from a binding without `result: true`; `crash` — a VM or emitted-code fault, a wasm trap, any unmarked raise; wasm never imitates a host raise (492, 527, 546, 675). A `crash` prints `crash: <the engine's reason>` on each target; a cell claims `stderr crash:` alone (556). An uncaught run-time abort writes to stderr the `Failure` an `attempt` would have caught, `<kind>: <message>` — `panic: division by zero: / on f64 at <file>:<line>:<col>`, `crash: <reason>`, `host: <message>` —, never the raw `Class:Reason` term; the departure declared in a cell is only whether the target aborts (535, 675). `attempt` on wasm uses wasm exception handling (`try_table` / `throw`) on every host, so `attempt({ -> panic("x") })` answers `Error(Failure(message: "x", kind: "panic"))` as elsewhere (518, 491, 543). A library sidecar that unwinds with a thrown term through a `host`-wrapped call is a library gap, never a compiler mechanism (554); `rakun-bpp`'s navigation signals become data its renderer reads (527 (5), 504).

(4) **Hosts and std.** `result: true`, `HostError` and the wrapping rule are § host-functions (4) (490, 489, 488, 546). Every action answers `Result` (303) and every store `Result<T, StoreError>` (304) — § actions-http-log-routing, § rakun.

## equality — `==` is structural, user code never runs

**`==` is structural on every target, a type cannot define its own equality, `f64` under `==` is a total order.**

## numbers-and-arithmetic — literals, widths, overflow, `bigint`, `Decimal`

**Kotlin's lowercase suffixes; a literal never changes type to fit; integer overflow is a program error on every target; `i64` is a real 64-bit integer everywhere; big numbers are exact.**

(1) **Literals.** `1.5` is `f64` and `42` `i32` by default; `1.5f` f32, `1.5d` f64, `42l` i64, `42u` u32, `42ul` u64, `42i8`, `42i16`, `42u8`, `42u16`, `42isize`, `42usize`; an uppercase suffix is a located error naming the lowercase one; a literal without suffix never changes type to fit: `val f: f32 = 1.5` and `val x: f64 = 1` are errors (247). A `bigint` literal carries the suffix `n` (332 (1)). An integer literal past its type's range is refused by the checker on every target (319).

(2) **Overflow and ranges.** Integer overflow is a program error on every target: `+`, `-`, `*`, unary `-` and the compound assignments of every integer type check the result against the declared type's range and abort; commonJS and erlang / beam add a range test per operation; no target wraps or answers a wider number (264). `abs` aborts past its type as unary `-` does, declared per width (`I32`, `I64` — now the types `i32`, `i64`, 641), `lo64().abs()` aborting on every target (496). `i64` and `isize` are −2^63 … 2^63 − 1, `u64` and `usize` 0 … 2^64 − 1, on every target; on commonJS a hybrid representation — a value within ±(2^53 − 1) a JS `number`, one beyond it a `BigInt`, always in that canonical form (`5` is never `5n`), each operation keeping its fast path and promoting only when the result leaves the safe range, 264's check aborting past the type's own bounds; the narrower integers stay JS numbers; crossing to JavaScript is explicit and exact (`toF64()`, `toI32()` abort when the value does not fit); a Node host template receives and answers `number | bigint`; the `.d.ts` types them `number | bigint` (319). `string.parseInt()` answers `Error` past the `i64` range (176, 319).

## types-enums-and-patterns — type tests, enums, `case`, namespace types, `?T`

## records-and-props — construction, spread, a component's props

**A record constructor evaluates its arguments in written order; `..` is the one spelling of the rest; a spread copies field values only, typed by structure; a component's props are plain parameters or one record parameter.**

(1) **Spread.** `val pessoa = Pessoa(..pessoaOld, nome: "Ana");` — `..src` at the start of an argument of a record constructor; `...` is only the inclusive range `a...b`; `botopink format` migrates `...` spreads to `..` (359 (1), 529 (3)). Arguments apply left to right, the later winning; several spreads and labelled fields mix; a field written explicitly twice is an error (359 (3)). Every field without a default must be supplied; a missing field is an error at the call (359 (4)). A component's attributes are the fields of its props; an undeclared attribute, a value of another type and a field with no default left unwritten are comptime errors at the attribute (192); a component's content is its default slot, read with `<Slot />` — no `children` field (193, 360). ## contexts-and-components — `Component<R>`, `RenderScope`, `use`, contexts and the hooks list

**A component is a lambda over an opaque `RenderScope`; calling it only makes the lambda and the render library runs it; a context is named by its value's type, read through an imported context value, provided by `use provide(ctx)`; every `use` is top-level and runs on every call.**

(1) **The wrapper and the lowering.** `Component<R>` is the only wrapper — no `@Hook`: a `Component<R>` whose `R` implements `Renderable` is called as a tag or a function, any other `Component<R>` is read with `use` (354 (1), 553 (2)). At run time a component is a lambda over an opaque `RenderScope`: `component fn Card(item: Item) -> View` lowers to a function answering `(scope) => …`; the call `Card(i)` runs nothing, so `itens.map(Card)` answers lambdas and generic code needs nothing of a component (388 (1), 653). std's `context` module declares `RenderScope` — opaque, made only by `RenderScope.root()` — and `c.run(scope)`, answering the result and the scope its body's `provide`s made for its children (388 (2)). The render library — `rakun-bpp`'s renderer — holds scopes explicitly: the root with `RenderScope.root()`, each child with the scope its parent answered, a kept value with the scope it kept (388 (3), 414). Inside a body `await c` runs `c` with the body's children scope; outside every body a value runs with `c.run(RenderScope.root())`; at build the comptime runtime runs it with `RenderScope.root()` (388 (4), 378 (4)). The scope travels explicitly: no "current context" stack, no `AsyncLocalStorage`, no process dictionary, nothing captured (388 (5)). Components compose by data on every target: only a body that awaits is a state machine, the renderer awaits only marked lambdas; a component that composes others stays direct; the tree it answers holds component values (`<main>{view()}</main>` stores `view()`'s lambda); `Suspense(fallback, child)` and `ErrorBoundary(child, view)` are tree nodes holding component values, run by the renderer while descending — inside a `Suspense` the child is rendered with the scope the node was met with; if the subtree finishes without a marked lambda the HTML is emitted directly; at the first marked lambda the fallback is emitted, `(child, scope)` kept, and the fill runs `renderComponent(child, scope)`; `ErrorBoundary` runs its child under `attempt` and renders `view(infoFor(failure))` with the same scope; a page with no marked node renders without streaming (504, 414). Every form is a component — a method, a lambda, a `default fn` answering `Component<R>`, and a type implementing `Component<R>` whose `render(self)` is its body (593; § records-and-props (3)). A `component` lambda runs as a `component fn` (574). Being a component asks no `await` of its callers (661). Hooks live in a `component fn` body — the marker is what admits `use` (553, 722).

(2) **Contexts.** A context always declares its default, named by its value's type: `pub val themeContext = comptime createContext(Theme(primary: "#e11d48", radius: 4));` in any module (378 (1), 379 (1), 722). A context is read through a context value the reader imports — `import {themeContext} from "theme"; … val t = use context(themeContext);` — never a bare type name; `t` is a `Theme`; the read answers the nearest context of that type provided above, else the default the handle carries; the handle is imported as any name, so no catalogue is searched (722, 723). `use provide(ctx)` takes a context value alone — there is no `(ctx, value)` form; a component that provides another value makes a context of the same type in its body, `val c = comptime createContext(Theme(…));` (a build value) or `val c = use memo({ -> createContext(Theme(…)) });` (run time: std's `memo<T>(make: fn() -> T) -> Component<T>`, computed on the component's first render and kept for that instance, never recomputed, no dependency list — 755; an instance is the value one component call makes, one slot per `use memo` position allocated with it — process dictionary or ETS on the BEAM, a closure cell on commonJS, a heap cell on wasm — 771), then `use provide(c)`; `use provide(themeContext)` provides the declared default again; the value goes to everything that component renders below it — descendants only, the nearest provider wins (723, 379 (2), 354 (2)). A context's identity is its type: two contexts over one base type are two types (`type Idioma(code: string)`, `type Moeda(code: string)`) (723, 379 (5)); two same-named types of two packages are two contexts (635 → 603). No unbound read: a context whose absence is a bug says so through its default (`StyledSheet.missing()` panicking at use) (378 (3)). When the default is computed: with `comptime` written, at build, a `Run` default refused; without, by its stage; a read at build needs a default known at build (378 (2)). A read is known at build when every `createContext` that can reach it through the hooks list is of build and all give one value, or none reaches it (379 (6)). `createContext(value, Behavior)` keys a context by the behavior its value implements, the value checked at build to implement it; `use inject(Deps)` builds a record whose every field is the nearest context of its field's type, else that type's declared default, else the field's own default, else an error at build naming the field; `T` a record, a behavior refused; nothing constructed recursively (416). std's `Context<T>` holds `contextValue: T`, and at run time a context is its plain value (683). A context declared `#[serverOnly]` / `#[clientOnly]` restricts its readers (354 (5)); a `#[client]` island reading a context provided outside it receives the value in its payload when `T` is encodable, sealed for a server island (354 (6)). ## wasm-target-and-runtime — hosts, WasmGC, the hand-written runtime, std's wasm forms

**A wasm build binds to the runtime it runs on; a program's values are WasmGC's; the language's wasm runtime is hand-written `.wat`, its logic in botopink; a wasm program answers as every other target does.**

(1) **Hosts.** Two profiles built together: `wasi` — wasmtime and the runtimes that follow WASI preview 2 (`wasi:http`, `wasi:clocks`, `wasi:io/poll`), the default — and `browser` (JS imports: `fetch`, `setTimeout`, `Promise`; node runs it too); std binds a cell on both hosts or on neither, and the wasm column of every cell runs under wasmtime and under node (334 (1)); the manifest names it, `"wasm": { "host": "wasi" }` (334 (2)); `host:` only where the hosts truly differ, one adapter list for both — each `wasi:` adapter has a preview 2 implementation and a JavaScript one (334 (3), 394). (2) **Memory and values.** The fronts of the linear-memory model are discontinued and unified in front 164 wasm-gc: B-82 the engine (wasmtime native, the page's on the web, wasm3 removed), B-83 the wasm codegen emits WasmGC for every value (`needs: [.Gc]`; no linear-memory value; a task's settled value shared, never copied; no heap per task), B-84 std-wasm rewritten (its logic in botopink, its leaves in hand-written `.wat`; `std_wasm.wasm`, `heap.zig`, the term library and `modules/beam-to-wasm/` deleted), B-85 Conformance; B-30 closed as superseded; until B-83 lands a wasm program allocates as today, a bump heap, exhaustion a trap — a known limit of a long task, written in the reference (544; amends 434, 440, 448, 449, 450, 452, 522). (2) **The `.snap` format.** `botopink-cell 1` on line 1, one record per line, in a fixed order, written and read in one place (`cell_snap.zig`): `out <text>` (a bare `out` an empty line), `no-final-newline`, `abort` (the exit status never pinned), `stderr <text>` (after `abort` only; a containment claim), `refused <message>` / `at <file>:<line>:<column>`, `label <text>` (475 (2), 485); a refusal and program output never share a file; a header alone is the empty answer; a departure replaces the module's whole `output/` answer on that target; a module's snapshot is named after its source; a refusal with no location is `main`'s; a majority is strictly more than half the targets; an empty answer is never accepted by default (475). A refusal prints `error[<code>]: <message>` (557); a `crash` cell claims `stderr crash:` alone (556).

(3) **`botopink cell`.** `cell new <path>` scaffolds a cell; `cell check <cell|directory>` compiles and runs each cell on every target it declares — beam executed through `erlc +from_asm` and `erl` (8) — and compares: equal → exit 0; different → a `<file>.snap.new` candidate beside it, exit 1 — the accepted snapshot is never overwritten; a new cell gets candidates (every target agreeing → `output/…snap.new`; a target departing → `output/` from the majority and `targets/<t>/…snap.new`; no clear majority → one candidate per target, the choice a person's); no update flag — a person accepts by renaming (464). One implementation in `compiler-cli`, run by the in-process runner, the pipeline's `cells` job and the libraries' gate stage (464 (5)).

(4) **The reference.** Every example in the language reference is a cell: `conformance/docs.md` holds the index and the text no single cell owns, `conformance/modules/<cell>/docs.md` the text for what that cell shows; botopink-lang's `docs.md` and `docs/` moved there, the manifest schema with them, no copy (461, 462, 466). ## gate-and-ci — the gates, the pool, the pipeline and landing

## bpp-files — the `.bpp` format, its unfold and its prelude

**A `.bpp` file is another spelling of a `.bp` module, unfolded by the toolchain onto the default function of the package `"bpp"` names; the toolchain knows the four `bpp` roles and nothing else.**

(1) **The format.** The header starts on the first line, with no opening `---`, and ends at the first separator line — `---` (the markup follows, to the end of the file) or `--- style ---` (the style section, closed by `---`, then the markup); a file with no separator is markup only; a first line `---` is an error at the line (212, 338 (7)). The header is ordinary botopink copied into the module as written — imports in the language's own form, `val`, `type`, `pub` — and reads top to bottom: its declarations (`import`, `type`, `fn`, `pub`) come first, its statements (`val`, `use`) after; a declaration below a statement is a located refusal naming the statement before it (198, 552). `type Props(…)` in the header is the convention: `card.bpp` unfolds to `pub default fn (..props: Props) -> View`, with none `pub default fn () -> View` (the unfold writes the `component` marker, `pub default component fn (..props: Props) -> View`, 731 (10)); the header's statements become the function's body ahead of `return <default> @`…`;`, so they may read `props` and call a hook; its caller passes the fields by label (199, 529 (5), 275). A `.bpp`'s decorator is written in the header, on a line just before the separator, annotating the unfolded function; no decorator comes from a file's name (221, 285). The module's anonymous `pub default fn` is named by its importer after the file: `components/PostCard.bpp` → `import {components.PostCard};`; a file named otherwise is imported with an alias; a file name that is no identifier is imported with the backtick form or an alias; no case conversion anywhere (213, 289, 561). The function returns the `R` of the default function's declared return (`View` for `rakun-bpp`) whether or not the header uses `use` or `await` (275, 578). The markup is the literal handed to the default function; a diagnostic inside it lands on the `.bpp` line (198). The style section unfolds to `use <style> @`…`;` in the function's body, after the header's statements, before `return`; one style section; errors at the line: a `--- style ---` after the markup, a second section, an unclosed one, a section in a project whose `"bpp"` package declares no `#[bpp.style]` function (338 (7)). `<style>` in markup is refused, naming the style section, except `<style #[isInline]>` (338 (8)).

(2) **The roles.** std's module `bpp` (`libs/std/src/bpp.bp`, `import {bpp} from "std";`) declares four annotations — `html` (the markup's unfold target), `htmlPrelude`, `style` (the style section's unfold target), `stylePrelude`; `#[bpp.html]` and `#[bpp.style]` go on the two template functions (`#[bpp.html] pub default fn html(syntax t: string) -> View`); the manifest names one package, `"bpp": "rakun-bpp"`, and the toolchain finds the roles in it by `bpp`'s annotations — `html` exactly once, the others at most once (361, 198, 284). The roles are checked whenever the manifest's key is present, `.bpp` file or not, on every `build` / `check` / `run` / `test` (709). The toolchain knows these things and nothing else: the package `"bpp"` names and the declarations the four annotations mark; a file's role (page, layout, …) is the framework's rule — the file-convention route table rakun-app generates calls `page` / `layout` / … on each unfolded default function; the toolchain applies no decorator by file name; `"bppKinds"` is gone (285). `html` is the `pub default fn` of the package `rakun-bpp`, carrying `#[bpp.html]`; `import html, {Element, renderToString} from "rakun-bpp";` (200). jhonstart, with -html, -link, -forms and -test, is now the workspace package `rakun-bpp`, a package named by its directory (724); the rule is unchanged — the manifest's `"bpp"` names the one package whose `#[bpp.html]` function is the unfold target (361).

(3) **The prelude.** The prelude is the items marked `#[bpp.htmlPrelude]` where they are declared, one by one: a marked `pub val` / `pub fn` / `pub type` of any module outside `src/internal/` is in the prelude, so a `.bpp` sees it by its plain name without importing (`#[bpp.htmlPrelude] pub fn Card(…)`, `<Card/>`); a `pub` item without the marker is the library's API; imports are private, none reaches a `.bpp`; no name is shadowed — two marked items of one name, or a `.bpp` that declares or imports a name the prelude gives, is refused, located, naming both; refused: the marker on an item without `pub`, on a `mod`, on a re-export of another package's item; `botopink prelude` and the language server list a package's prelude (589, 592 (9)). The prelude is the module's last scope, consulted only for a name the file does not bind; an item becomes an import only when a name of the file resolves through it, and the emitted code imports the same; the header wins by scope order; the scope is generic — a list of import items handed to `compiler-core`, naming no library; a markup-only `.bpp` compiles (270, as amended by 589). A marker is a decorator with an empty body (604).

## markup-and-rakun-bpp — tags, holes, slots, directives, native elements

**A tag's attributes are its component's props; a hole accepts a closed list the template decides; a component's content is its default slot; template directives are annotations written inside the tag; a native tag is typed as React types its intrinsic elements.**

(1) **Holes and nodes.** `rakun-bpp`'s templates accept in `{expr}` a closed list: a `string`; a number of any numeric type and a `bool`, each as its `toString()` text; a component the template renders (a `Component<Element>` value); a list of such components; and `Node`, the name of that set — `import {Node} from "rakun-bpp";`, replacing `JhonstartNode` and `Children`; any other type is a comptime error at the expression (191, 223). ## pages-routing-and-stages — `#[page]`, the render stage, request and response, islands

**The stage a page renders in is a compile-time fact read off the hooks list; no role is declared by an export's name and no segment configuration exists; a page reads its route through hooks; a route handler is always server.**

The frameworks' markers (`#[serverOnly]`, `#[clientOnly]`, `#[page]`, `#[client]`) are `rakun-bpp`'s decorators read against the hooks list, the compiler naming no stage, marker or library (277). (2) **Roles and settings.** No role is declared by an export's name: the pages to prerender, the page's head, a partial page, an OG image, a content collection are said in a decorator — `#[page("blog/[slug]", paths: allPosts, head: postHead, partial: true)]`, `#[ogImage(…)]`, `#[collection(…)]` — typed; the framework never looks a function up by its name, and one left in a module is an error naming the decorator form; route file names stay the routing convention (282, 236). A route file's header may import and write its kind's decorator without binding a name twice (289).
