Empirical results worth recording:
- `typeDefinition` on `val p = Point(1, 2)` with the cursor at **(1,4)** returns
  `(0,7)–(0,12)` from the live server, and at (1,5) returns `null`. The row's "expected" is exactly
  right, and the extra suggestion to rewrite the fixture as `Point(x: 1, y: 2)` is unnecessary —
  the positional fixture compiles as is.
- **Withdrawn:** "`p: i32` has no `distance` method, so the fixture does not compile"
  (`semantic_tokens_member_access`). It *does* compile: `botopink check` on
  `fn dist(p: i32) -> i32 { return p.distance(); }` is clean and the server publishes no
  diagnostics (an unknown method on a receiver is not an error today; the same holds for
  `r.nope()` on a record). The row's real point — the `property` branch is never exercised —
  stands.
- **Withdrawn:** the criticism that the `completion_number_prefix` test comment "mixes up
  characters and caret positions". `source[15] == '2'` is literally true, so the comment is
  accurate; only its phrasing is loose. The coverage gap (Case A untested) stands.
- `completion_decorator_body_locals` really is on the degraded path: the server publishes
  `unbound variable 'items'` for that fixture, so `bindings()` is null and the fallback
  local-scope list is what the snapshot pins.
- `completion_no_match`'s source really does fail the compile pipeline (`botopink check` →
  `parse failed for module 'main'`), so its bindings are empty — the mechanism differs slightly
  from the first pass's wording (the formatter's parser accepts `val zzz`), the conclusion does not.
